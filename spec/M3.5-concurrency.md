# Farmos M3.5 — Concurrent Tasks (Multithreading) Specification

**Status:** FINAL (PM-approved 2026-09-29)  
**Milestone:** M3.5 Multithreading (concurrent tasks) — PLAN.md, added 2026-09-29  
**Depends on:** `spec/M1-core.md` (FINAL + Rev 2), `spec/M2-math.md` (FINAL), `spec/M3-scene.md` (FINAL)  
**Normative keywords:** MUST / SHOULD / MAY per RFC 2119.

This document specifies structured concurrent tasks for Farmos, **compile-time data-race (conflict) detection**, the memory and output-ordering model, function effect summaries, diagnostics (E0801–E0807, W0801), the runtime contract, acceptance criteria, and the M3.5 test index. It does **not** specify compiler/runtime/stdlib implementation code.

Related: `/workspace/farmos/PLAN.md`, `spec/M1-core.md`, `spec/M2-math.md`, `spec/M3-scene.md`, `spec/tests/M3.5/README.md`.

**Target platform (PLAN.md):** Windows x64 only; C backend via clang or gcc (MSVC `cl` unsupported); fully local. Size ACs use the Windows x64 stripped PE. The language rules below are backend-neutral; backend notes are non-normative (Appendix B).

## 1. Scope and non-goals

### 1.1 In scope (M3.5 MUST implement)

- The `parallel { task { … } task { … } … }` statement (structured fork/join, §3).
- Execution and memory model (§4) with the **sequential-equivalence guarantee** (§4.6).
- Conflict definition, locations, and **static conflict analysis** (§5–§7): compile error for different/unknown-value write/write (E0801) and read/write (E0802) overlaps; **warning** for equal-constant write/write (W0801).
- Effect summaries of user functions, methods, and standard-library calls (§7, §8).
- Deterministic output (`print`/`println` buffering, §9) and deterministic trap selection (§10).
- Runtime worker pool with observable behavior independent of worker count (§11).
- Diagnostics: E0801–E0807, W0801, warning/note format, `--werror` (§12).
- Fixture pack `spec/tests/M3.5/` (108 fixtures) with harness extensions (`# repeat`, `# threads`, `# warning`, `# note`, `# flags`, `# diag_exact`).

### 1.2 Explicit non-goals (M3.5 MUST NOT require)

| Deferred / rejected | Note |
|---------------------|------|
| Atomics, `Atomic<int>`, mutexes, condition variables, channels, message passing | **Non-goal.** Tasks cannot communicate while running; the only communication is fork (parent → task) and join (task → parent). A future milestone MAY add reductions/atomics; nothing in M3.5 may preclude them. |
| `spawn f(x)` / handles / `join()` / `await` / `async` | OQ-M35-01 (structured block chosen). |
| Promise.all-style APIs | Needs function values (M1: none). OQ-M35-01. |
| Task return values, cancellation, timeouts, priorities | Not needed; results flow through assignments to outer locations. |
| Dynamic task counts, `parallel for` | Task count is fixed by the source (≤ 256). Future work. |
| Mutable global variables | M1 has only top-level `const` (immutable). No global race surface exists. |
| GPU / SIMD parallelism | Later milestones. |
| Runtime conflict detection | Not required and not present in M3.5 (RD-M35-01). Exit code 109 is reserved, unused (§13, OQ-M35-02 option C). |
| Parallel rendering internals (tile/row parallel rasterizer) | M4; must obey the same rules. |

### 1.3 Design constraints

- PLAN.md M3.5: concurrent independent tasks run correctly; conflicting writes are an error that is reported; non-conflicting shared reads are legal; hello world unchanged in size; fixtures under `spec/tests/M3.5/`.
- M1: no closures / first-class function values; semicolons required; per-module scoping; program-lifetime arena; diagnostics `path:line:col: error[E0xxx]: msg`.
- **PM decisions (2026-09-29), normative:**
  1. Conflict detection is **compile-time static**; no runtime conflict trap.
  2. Same location, **same statically-known value** in two tasks → **warning** (W0801), compile succeeds, exit 0.
  3. Same location, **different** statically-known values → **compile error** (E0801), exit 1, both locations reported.
  4. One task **reads** and another **writes** the same location → **compile error** (E0802, distinct from write/write), exit 1.
  5. Unknown values / possibly-overlapping locations: **OQ-M35-02** (recommended: option A, conservative error).

## 2. Design summary and syntax alternatives (informative rationale, decisions are normative in §3)

### 2.1 Alternatives evaluated

| | (A) Structured block `parallel { task {…} … }` | (B) `spawn f(args);` + handle `join()` / `await` | (C) Promise.all-like API |
|---|---|---|---|
| Fits M1 (no closures, no generics) | **Yes.** Task bodies are lexical blocks, not values; they cannot escape. | Partly. A handle type needs a result type: without generics each callee type needs its own handle type; a handle is a first-class-like value that can escape or be dropped unjoined. | **No.** Needs function values (closures) or an array of callables; M1 forbids both. |
| Conflict scope | **Lexical**: the block. All accesses are visible in one syntactic region → precise static analysis. | Dynamic: the interval between `spawn` and `join` follows control flow; handles can be stored, passed, conditionally joined → analysis needs alias/flow tracking. | Same problems as (B), plus opaque closures. |
| Determinism | Fork/join at block edges → sequential-equivalence (§4.6) is easy to guarantee. | Join order is program-defined but needs a discipline to keep output/order deterministic. | Same as (B). |
| Three.js/TS feel | `Promise.all`-like intent, block syntax; reads like a C#/Go/Kotlin scope. | Familiar to TS users (`await`) but `await` is future-reserved (M1 §2.5) and implies `async`. | Most JS-like but impossible in M1. |

**Decision (RD-M35-02): (A) structured concurrency is the M3.5 default and only task syntax.** Rationale: it is the only form implementable under M1's constraints without adding generics or closures, it makes conflict scopes lexical (enabling PM decision 1: static detection), and it makes results deterministic by construction (§4.6). (B) and (C) are recorded as **OQ-M35-01** with a recommendation to revisit (B) only after generics land.

### 2.2 How tasks receive data (normative summary)

- A task body is a block that **lexically sees** everything visible at the `parallel` statement (enclosing locals, parameters, `this`, module-level names) — by reference to the same storage, not by copy (§4.2). This is not a closure: a task cannot outlive its `parallel` statement, cannot be stored, and is not a value.
- A task **returns nothing**; results are delivered by assigning to locations declared before the block (a local, a field through a reference, an array element). Conflict rules (§6) guarantee no two tasks write or read-write the same location, so results are unambiguous.
- Locals declared inside a task are task-private (§4.3).

## 3. Syntax

### 3.1 EBNF (amends M1 §3.5 `stmt`)

```
stmt          ::= let_stmt | const_stmt | assign_stmt | expr_stmt | if_stmt
                | while_stmt | for_stmt | break_stmt | continue_stmt
                | return_stmt | block
                | parallel_stmt                                   (* NEW *)

parallel_stmt ::= "parallel" "{" task_item+ "}"
task_item     ::= "task" block
```

- `parallel_stmt` takes no trailing `;` (same rule as any block, M1 §2.10). It is a statement, not an expression; it has no value.
- It MAY appear wherever a statement may appear: function, method, and constructor bodies; inside `if`/`while`/`for` bodies; inside a task body (nested, §6.9). It MUST NOT appear at module top level (top level admits only declarations, M1 §3.1); a token sequence `parallel {` there is `E0202` (unexpected token).
- `task_item`s are separated by nothing but the block structure; each is `task` followed by a `block`.

### 3.2 Keywords: contextual, not reserved (RD-M35-03)

`parallel` and `task` are **contextual keywords**. They are **not** added to the M1 reserved list (§2.5) or the future-reserved list. Collision check against M1 §2.5 (reserved: `bool break class const constructor continue else export false float for function if import int let new return string struct this true void while`; future-reserved: `as async await enum extends implements in interface match mut null optional private protected public static super switch type typeof var yield`; M2 adds `operator`): **no collision.**

Recognition (1-token lookahead, no backtracking):

1. `parallel` is the keyword **iff** it is the first token of a statement **and** the next token is `{`.
2. `task` is the keyword **iff** it is the first token of a `task_item` (immediately after `parallel {` or after the `}` that closed the previous `task_item`) **and** the next token is `{`.
3. If a statement begins with `task` followed by `{` anywhere other than rule 2 (outside a `parallel` body, or directly inside another task body), the compiler MUST report `E0806` at the `task` token.
4. Everywhere else the two words are ordinary identifiers: variables, parameters, fields, functions, types (fixtures 024).

**Compatibility with existing M1–M3 programs:** every program that compiles under M1–M3 keeps compiling with the same meaning, with one pathological exception that is accepted as a documented incompatibility: an *expression statement* that is a brace struct literal of a struct literally named `parallel` or `task` at statement start (`parallel { x: 1 };`) — legal but pointless in M1 (value discarded) — now parses as a `parallel_stmt` and fails. No shipped fixture or stdlib name is affected.

### 3.3 Grammar restrictions

- A `parallel` body MUST contain at least one `task_item`, and every item directly inside it MUST be a `task_item`. An empty body or any other token where `task` is expected → `E0202` at that token (the closing `}` for an empty body; the first token of an intruding statement, e.g. `let`; fixtures 048, 051).
- A `parallel` block MUST contain **at most 256** tasks; the 257th `task_item` → `E0807` at its `task` token (fixture 052). Rationale: bounded per-block bookkeeping; task indices fit in a byte.
- **Task index:** tasks of a block are numbered **1, 2, …, n in source order**. This numbering is used in diagnostics, output ordering, and trap selection (deterministic and independent of scheduling).
- A `parallel` block with one task is legal (degenerates to a call).

### 3.4 Static rules inside a task body

Task body is a block with the usual M1 scoping (§5.1) plus:

- `return` anywhere inside a task body (including inside loops/ifs in that body, excluding bodies of nested *functions*, which are not lexically inside) → `E0803` at the `return` token.
- `break`/`continue` whose nearest enclosing *loop-or-task boundary* is the task (i.e. no loop between the statement and the enclosing `task { }`) while a loop exists outside the task → `E0804` at the keyword token. If no loop exists at all, the M1 error `E0510` applies unchanged.
- A call whose effect summary includes file output (§7.5) → `E0805` at the call expression.
- `task` where `parallel` body context is absent → `E0806` (§3.2 rule 3).
- All M1 rules (`E0504` const assign, `E0505` undefined name, type errors, …) apply unchanged. A sibling task's locals are not visible (`E0505`, fixture 050).
- M1 `E0509` (unreachable after `return`) is unaffected; a task body needs no return and simply falls off its end.

## 4. Execution and memory model

### 4.1 Definitions

- A **parallel block execution** is one dynamic execution of a `parallel` statement. It forks tasks 1..n, then **joins** (waits for all) before the statement after the block runs. There is **no other synchronization primitive**.
- A **task** is one execution of one `task_item` body. It runs on some thread, chosen by the runtime, unobservably (§11).
- A **location** is a named piece of mutable storage as defined in §5.

### 4.2 What a task can see

A task body sees exactly what a plain block at the same point would see (M1 §5.1, §5.5):

| Name | Visible? | Sharing |
|------|----------|---------|
| Enclosing locals / parameters (`let`, `const`, params, loop variables declared outside the block) | Yes | **Shared storage** (same location as the parent; not a copy). |
| `this` (inside methods/constructors) | Yes | Shared reference (struct methods: by-reference `this`, M2 §3.2). |
| Top-level `const` and top-level functions/types (own module + imports) | Yes | Immutable (M1 §4.9): reading is never a conflict. **Farmos has no mutable globals.** |
| Class fields through a reference | Yes | The referenced object is **shared** between all tasks holding a reference to it (M1 §4.7 reference semantics). |
| Array elements / struct fields of a shared variable | Yes | Sub-locations of the shared variable (§5). |
| Locals declared inside another task | **No** (`E0505`). | — |

### 4.3 What is task-private

- Every local (`let`/`const`, `for` variable, parameter of a called function) **declared inside the task body**, including locals that shadow outer names (fixtures 003, 075).
- Local *struct and fixed-array* values declared in the task, including copies (`let q: Pair = p;` copies, M1 §4.6; fixture 019).
- Locals of functions called from the task (each call has its own frame).
- Objects **allocated inside the task** (`new C(...)`, directly or in callees) and reachable only through task-private bindings (§4.8).
- The task's output buffer (§9).

Effects on private storage are invisible to other tasks and are excluded from conflict analysis.

### 4.4 Copied vs shared (explicit)

| Kind | On `let b = a;` / argument passing | Two tasks holding `a` / a reference |
|------|------------------------------------|--------------------------------------|
| `int`/`float`/`bool`/`string` variable | Copy | Same variable ⇒ same location (shared, subject to §6). |
| `struct` value (M2 math types included) | **Copy** all fields (M1 §4.6) | Same variable ⇒ shared locations `v`, `v.x`, …; a copy made *inside* a task is private. |
| Fixed array `T[N]` | **Copy** (M1 §4.5) | Elements are sub-locations `a[k]`. |
| Dynamic array `T[]` | M1 does not say whether `let b = a` / argument passing of a `T[]` copies or aliases the buffer (Gap G-1, §21). **The checker MUST be sound under both readings:** dynamic arrays are analysed with the *origin model of §5.3* (as if reference-like): `[]`/array literals are allocation sites, `let b = a` copies `a`'s origin, effects on a `T[]` parameter are instantiated on the argument. | Length `a.#len` and elements `a[k]` are sub-locations. |
| `class` instance | **Reference copy (alias)** (M1 §4.7) | Two tasks holding refs to the same object share every field; overlap is decided per field path (§5.3). |

### 4.5 Memory-model guarantees (happens-before)

1. **Fork:** every write performed before the `parallel` statement in the enclosing thread *happens-before* the first action of every task.
2. **Join:** every write performed by every task *happens-before* the first action after the `parallel` statement.
3. **No other edges:** there is no happens-before between actions of different tasks of the same block. §6 guarantees that no location is written by one task and accessed (read or written with a different value) by another; hence the absence of such edges is unobservable. (The one tolerated overlap — equal constant writes, W0801 — is race-free by §6.2.)
4. After join, a location written by exactly one task holds that task's last write to it; a location written by no task is unchanged; a location written by several tasks with equal constants (W0801) holds that constant.
5. Program-lifetime arena allocation (M1 §4.7) MUST be safe under concurrent `new` and `push` from tasks (thread-safe allocator); no allocation address is observable, so this does not affect determinism.

### 4.6 Sequential equivalence (normative theorem)

For any program the compiler **accepts** (no E0801/E0802 in any parallel block), every execution — any thread count, any schedule — MUST produce the same observable behavior (stdout bytes, stderr bytes, exit code, final values of all locations) as the **sequential reference execution**: run each parallel block by executing task 1 to completion, then task 2, …, then task n, on one thread, stopping at the first trap (§10.2). This is the specification of what "run correctly" means for AC-M35-01; the fixtures' expected outputs are computed by this reference semantics.

Corollary: the program is deterministic in the presence of W0801 warnings too (§6.2).

### 4.7 Values after join

After join, all task effects are visible (§4.5.2). Struct/array/class effects are ordinary writes to the original storage. A parent MAY read any location any task wrote. Nothing is "returned" from tasks other than via such writes.

### 4.8 Objects allocated in tasks

A `new C(…)` executed by a task creates an object owned by that task until published. It is *published* by a write to a shared location (e.g. `cs[0] = t;`, fixture 026) — that write is itself checked under §6. Effects on an unpublished object through task-private bindings are private (excluded from conflict analysis). The arena keeps the object alive after join (M1 §4.7).

## 5. Locations, access sets, overlap

### 5.1 Granularity (normative)

The unit of conflict is the **access path**:

```
path  ::= root step*
root  ::= variable-binding            (* int/float/bool/string/struct/array local or parameter *)
        | object-origin               (* a class instance, see §5.3 *)
        | Graph | Tree(origin)        (* stdlib abstract locations, §8.3 *)
step  ::= "." field                   (* struct field or class field *)
        | "[" index "]"               (* array element, see §5.4 *)
        | ".#len"                     (* dynamic-array length/storage header *)
```

- **Variable**: `a`. **Struct field**: `p.left`, `mesh.position.x` (every leaf component of inline structs is its own location). **Class/object field**: `c.n` (a field of *that object*). **Array element**: `r[2]`.
- Two locations conflict only if their paths **overlap** (§5.5). Distinct fields, distinct constant indices, distinct objects, and distinct variables never overlap.
- Object granularity is **per field**, not per object (RD-M35-06): two tasks may write different fields of one object (fixture 008), including different leaf components of inline math fields (`position.x` vs `position.y`, fixture 078).

### 5.2 Access sets

Every expression/statement contributes reads and writes; a *site* is the source position of the access (§12.2).

| Construct | Reads | Writes |
|-----------|-------|--------|
| Use of variable / path in an expression | that path | — |
| `lv = e` | reads in `e`; reads of variables in `lv`'s index/receiver sub-expressions | `lv` (value: §5.6) |
| `lv ⊕= e` (M1 §5.13) | as `=` **plus** `lv` | `lv` with **unknown** value (§6.5) |
| `a[i]` (element access, read or write) | `i`; **`a.#len` if `a` is a dynamic array** (bounds check) | — (write: `a[i]`) |
| `len(a)` (dynamic) | `a.#len` | — |
| `push(a, v)` | reads in `v` | **`a`** (whole array: length and all elements), unknown value |
| `o.f` where `o` is a class reference | `o`'s binding, and the *location holding* `o` if `o` was loaded from memory (a dereference reads the reference) | write of `o.f` when assigned |
| Function/method/operator/stdlib call | reads of argument expressions | the callee's **summary effects** instantiated at the call (§7) |
| `println`/`print` | argument reads | none (output is buffered per task, §9; stdout is not a location) |

### 5.3 Objects, aliasing, origins (class references)

Every class-typed expression has an **origin**:

- `Site(n)`: a `new C(…)` occurrence, or a call site of a **fresh-return function** (a function whose every `return` expression is a `new` or a call of a fresh-return function; least fixed point; fixture 108). Each call site is its own site.
- `Param(k)`: parameter `k` (or `this`) of the function under analysis.
- `Unknown(C)`: loaded from memory (field, array element), returned by a non-fresh function, or held in a binding that is assigned more than once.

A binding's origin is the origin of its initializer if the binding is `const` or a `let` never reassigned; `let q = p` (binding to binding) copies `p`'s origin (so `q` **is** `p`: definite alias, fixture 061). A dereference of a reference loaded from memory *reads* that memory location (§5.2).

Object-root overlap (both roots of compatible class; classes are compatible if equal, or both in the M3 Object3D family, M3 §5):

| Roots | Result |
|-------|--------|
| Same `Site` / same `Param` | **Definite** (same object) |
| Two different `Site`s | **Disjoint** (fixtures 009, 079, 108) |
| Anything else of compatible class (`Param` vs `Param`, `Param` vs `Site`, any `Unknown`) | **Possible** (may alias) |
| Incompatible classes | Disjoint |

Value-typed variables (int, struct, fixed array, …) are roots named by their binding: two different bindings never alias; the same binding is Definite. A struct method's by-reference `this` is the receiver path (M2 §3.2).

### 5.4 Index analysis (array elements)

Each element step carries an **index form**, computed after constant folding (§5.6):

| Form | Source | Overlap with |
|------|--------|--------------|
| `Const(k)` | integer constant expression (`3`, `K`, `k + 1` with `const k`) | `Const(k')`: Definite iff `k == k'`, else Disjoint. |
| `Interval(lo,hi)` | index is the task-private variable `i` of a counted loop `for (let i = L; i < H; i += 1)` (or `<=`) with constant `L`,`H`, `i` not assigned in the body; also `i + c`, `c + i`, `i - c` (shifted). Empty if `L ≥ H`. | Intervals/consts: Disjoint iff ranges do not intersect; otherwise Possible. |
| `Sym(s, c)` | `s`, `s + c`, `c + s`, `s - c` where `s` is a single identifier declared **outside** the block and **written by no task of the block** | Same `s`: Definite iff same `c`, else Disjoint. Different `s`, or vs `Const`/`Interval`: Possible. |
| `Any` | everything else (calls, arithmetic on `let`s, dynamic indices from other arrays, …) | Possible with every index form. |

No constant propagation through `let` bindings (fixture 060: `a[i]` vs `a[j]` with `i = j = 1` is *Possible*, not Definite). Constant propagation through `const` is exact. Fixed-array out-of-range constant indices are not compile errors (M1 fixture 018) and are just further constants.

### 5.5 Overlap of paths

Two paths overlap iff their roots overlap (§5.3) and, comparing steps pairwise from the root, **no compared step pair is Disjoint**; when one path is a **prefix** of the other the remaining steps are ignored (a write to `p` overlaps `p.left`; a write to dynamic array `xs` overlaps `xs.#len` and `xs[k]`, fixtures 036, 081). The overlap is **Definite** iff every compared root/step is Definite; otherwise **Possible**. `xs.#len` and `xs[k]` do not overlap each other (siblings).

The **overlap location** used for messages (`{loc}`, §12.1) is the longer of the two overlapping paths, printed in source spelling: `a`, `p.left`, `c.n`, `r[2]`, `a[?]` (for `Interval`/`Sym`/`Any`), `Counter.n` when the root is `Param`/`Unknown`, `xs.#len`.

### 5.6 Statically-known values ("constant expressions")

A **constant expression** is one of: int/float/bool/string literal; a reference to a `const` binding (local or top-level) of primitive type whose initializer is a constant expression; unary `-`, `+`, `!`; binary `+ - * / % == != < <= > >= && ||` over constant operands with M1 semantics (int wraps; **an integer `/` or `%` by constant zero is not constant**; M2 §4A int-literal→float contexts apply); string `+`; a struct `new S(…)`/literal or fixed-array literal whose components are all constant. **Never constant:** calls of any kind (including `f()` that obviously returns 1, `str(1)`, `len(…)`), `let` variables (no propagation), parameters, fields, element reads, compound assignments (fixture 033), `push`.

Two constants are **equal** iff same type and identical value; floats compare by IEEE **bit pattern** (`0.0` ≠ `-0.0`, NaN equals NaN with the same bits; fixtures 095, 096); strings by UTF-8 bytes (`"hi" + "!"` folds to `"hi!"`, fixture 097). When the two writes cover different-depth paths, values are compared **restricted to the overlap location** (projection of a struct/array constant onto the sub-path).

The value of a write access is: the constant of its RHS if constant; else **Unknown** (also for `⊕=`, calls, `push`, and derived stdlib writes). Unknown never equals anything, including itself (`a = x` vs `a = x`, `a = f()` vs `a = f()`: fixtures 069, 068).

## 6. Conflict rules (static)

### 6.1 The four classes (normative summary of PM decisions 1–4)

Consider one parallel block and two different tasks `i < j`. For every pair of access sites `x` (in task `i`) and `y` (in task `j`) whose paths **overlap** (§5.5; Definite or Possible):

| Class | Condition | Result |
|-------|-----------|--------|
| **1. No conflict** | paths do not overlap (Disjoint), **or** both accesses are reads | accepted; no diagnostic |
| **2. Same-value write/write** | both write; on the overlap both written values are **constant and equal** (§5.6) | **warning W0801**, compile succeeds (exit 0) |
| **3. Different-value write/write** | both write; the values are not both constant-and-equal (different constants, or either Unknown) | **error E0801**, exit 1 |
| **4. Read/write** | one reads and the other writes | **error E0802**, exit 1 |

Priority when one pair of sites falls into several classes: **3 > 4 > 2** (E0801 over E0802 over W0801). Reads never inherit the leniency of class 2 (fixture 103). Two tasks *reading* the same location while **no** task of the block writes it is always legal (fixtures 004, 072, 082, 084, 102).

`Definite` vs `Possible` only changes the wording of the message (§12.1), never the class: under OQ-M35-02 option A a Possible overlap is treated exactly like a Definite one (fixtures 060, 062, 066, 067).

### 6.2 Class 2 — same-value writes: W0801

- The program compiles, links, and runs; farmc prints the warning (§12.1) and exits 0 (if there is no error elsewhere).
- Execution semantics are **defined**: after join the location holds the common constant (§4.5.4). Backends MUST NOT emit code with C-level undefined behavior for these stores (Appendix B).
- Equality is exact (§5.6): `a = 1`/`a = 1`; `a = 1 + 2`/`a = K` (const 3); floats by bit pattern; folded string concatenations. `a = x`/`a = x` with a `let x` and `a = f()`/`a = f()` are **not** class 2 (they are class 3).
- Possible-overlap same-value pairs (`a[i] = 1` / `a[j] = 1`) are class 2 as well (fixture 066); the message says "may".
- **Rationale for W (not E):** the outcome is schedule-independent and value-independent, so no observable nondeterminism exists; it is still a smell (the second write is redundant) and, unlike a purely value-dependent error, remains schedule-stable because the decision is made on statically known constants.

### 6.3 Class 3 — E0801

`a = 1` vs `a = 2` (the PLAN.md example, fixture 031); `a = 1` vs `a = y` (101); `a = x` vs `a = x` (069); `a = f()` vs `a = f()` (068); `push(xs, 1)` vs `push(xs, 2)` (039); `a[i] = 10` vs `a[j] = 20` (060); `-0.0` vs `0.0` (096); any pair involving a compound assignment (033, §6.5); mutating stdlib methods on one receiver (104).

### 6.4 Class 4 — E0802

A read in one task of a location that overlaps a write in another task, in either order of task numbers (032, 054, 062, 065, 073, 081, 083, 087). Reads include implicit reads: the index variable in `a[i]` (087), the bounds-check read of `a.#len` for dynamic arrays (083), and reads performed by summaries (054: `c.get()` reads `c.n`).

Distinct error code from write/write (RD-M35-05) so tooling and users can tell "lost update" from "torn read".

### 6.5 Compound assignment (normative rule)

`lv ⊕= rhs` is a **read of `lv` followed by a write of `lv` whose value depends on the read** (M1 §5.13). The site therefore has read-set ∋ `lv` and write-set ∋ `lv` with value **Unknown**. Consequently:

- `a += 1` in two tasks → E0801 (write/write, unknown value; fixture 033) — even though the increments "look" identical, the result depends on the interleaving of the read-modify-write.
- `a += 1` in task 1 and a plain read of `a` in task 2 → the write/read pair is class 4 (E0802), but if task 2 also writes → E0801 wins (priority 3 > 4).
- Compound assignments inside **one** task are unrestricted (§6.6).

The same holds for `a = a + 1` (reads `a`, writes Unknown) — the rule is uniform: values that depend on any read are Unknown (only constant expressions are known, §5.6).

### 6.6 Accesses within one task

All accesses of one task are ordered by the task's own control flow; write/write, read/write inside one task never conflict (fixture 018). A task observes its own writes immediately and never observes another task's writes (there are none that overlap, §4.5.3).

### 6.7 `push` and dynamic arrays

`push(a, v)` **writes the whole array `a`** (length header and element storage, since growth may reallocate) with Unknown value; it reads the expressions in `v`. `len(a)` reads `a.#len`; `a[i]` reads `a.#len` (bounds check) and `a[idx(i)]`. Consequences:

- `push(xs, 1)` in two tasks → E0801 (039); `push` in one task and `len(xs)` or any element access on the same array in another → E0802 (081, 083); different arrays (`xs`, `ys` from different allocation sites) are independent (021).
- Elements of a dynamic array may be written by different tasks through disjoint indices **provided no task pushes** (`a[i] = …` writes `a[idx]` and reads `a.#len`; `a.#len` is only *read*, so no conflict; fixture 007 uses a fixed array; with a dynamic array the analysis is identical).

### 6.8 Flow-insensitivity

The analysis ignores control flow: every site inside a task body counts once, whether or not it can execute (fixture 053, `if (flag) { a = 1; }`), and loops do not multiply sites. Constant conditions (`if (false)`) are not evaluated. Rationale: schedule- and value-independent, simple, and stable across compiler optimizations.

### 6.9 Nested `parallel` blocks

- A `parallel` block inside a task body is allowed to any depth (fixtures 013, 029, 046, 047).
- The inner block is analysed on its own (its tasks are numbered 1..m independently).
- In the **enclosing** block, all sites of the inner block (all inner tasks, in source order) are sites of the **enclosing task** (fixture 047: outer task 1's inner write `a = 1` conflicts with outer task 2's `a = 3`). Pairs of sites inside the same outer task are never compared by the outer block.
- Runtime: fork/join nests (§11.3). Inner blocks are joined before the enclosing task continues.

### 6.10 Reporting algorithm (schedule-independent, source-order-stable)

The analysis is a pure function of the program text. For each parallel block (analysed in source order, inner blocks first):

1. Collect the site list of each task (§5.2, §7, §8), tasks numbered in source order.
2. For each task `j = 2..n` and each site `y` of task `j` **in source order**:
   1. Find the **lowest** `i < j` such that some site of task `i` conflicts with `y` (class 2, 3 or 4).
   2. Among conflicting sites of task `i`, choose the one with the highest class (3 > 4 > 2), then the earliest in source order (line, col).
   3. Emit **one** diagnostic for `y`: primary location = `y`'s site position (§12.2); `note:` location = the chosen `x`'s site position.
3. **Site merging and noise suppression (normative):** (a) accesses at the *identical* source position form one site with the union of their reads/writes (e.g. the read+write of `a += 1`, or a call summary that reads and writes `c.n`); such a site yields at most one diagnostic. (b) If one *statement* of task `j` would yield several diagnostics whose overlap location is the same, only the highest-class, earliest one is kept (fixture 067: the write `y.n = …` is reported; the read `y.n` on its right-hand side is not reported separately). Reads and writes of *different* overlap locations in one statement are reported separately.
4. All diagnostics of the compilation are sorted by (path, line, column, code) and printed in that order (§12.4). Errors and warnings share the stream.

Consequences: with `n > 2` tasks, a site conflicting with several earlier tasks is reported once, against the lowest-numbered one (fixtures 065, 088, 089); a conflict is always reported at the higher-numbered task with the earlier task in the note (031: primary `a = 2;`, note `a = 1;`); conflicts are never reported at both ends.

### 6.11 Limits of static analysis — the OQ-M35-02 policy table

What counts as "value statically determinable" is §5.6 (constant expressions only; no propagation through `let`, no interprocedural constant propagation into callees). What happens for undeterminable values or unresolvable locations is **OQ-M35-02**. The normative text of this spec implements **option A** (recommended). Behavior per option:

| Example | Option A (conservative; **default here**) | Option B (unknown ⇒ warning only) | Option C (error if definite, else runtime check at join) |
|---------|--------------------------------------------|-----------------------------------|----------------------------------------------------------|
| `a = 1` / `a = 1` | W0801 | W0801 | W0801 |
| `a = 1` / `a = 2` | E0801 | E0801 | E0801 |
| `a = f()` / `a = f()` | E0801 | warning | E0801 (same variable ⇒ definite) |
| `a = x` / `a = x` (`let x`) | E0801 | warning | E0801 |
| `a = 1` / `a = y` | E0801 | warning | E0801 |
| `a[i] = 1` / `a[j] = 2`, `i`,`j` unknown | E0801 (possible) | warning | accepted; **runtime trap 109 at join** if `i == j` |
| `a[i] = 1` / `a[j] = 1` | W0801 (possible) | W0801 | W0801, no runtime check needed |
| `x.n = 1` / `y.n = 2`, `x`,`y` may alias | E0801 (possible) | warning | accepted; runtime trap 109 if same object |
| `a += 1` / `a += 1` | E0801 | E0801 (read+write, value-dependent) | E0801 |
| read `a` / write `a` | E0802 | E0802 | E0802 (definite) / runtime 109 (possible) |

Option A has zero runtime cost, is decided entirely at compile time, and is the only option under which "a program that compiles is race-free and deterministic" holds without any dynamic machinery. Its cost is false positives (e.g. fixture 067, 059). Users can eliminate a false positive by making disjointness provable (distinct `new` sites, distinct constant indices, counted-loop intervals, `Sym(s,c)` offsets; fixtures 007, 107) or by restructuring (each task writes only its own slot).

## 7. Function effect summaries (interprocedural)

Farmos M1–M3 has **no function values, no virtual dispatch, no inheritance** (M1 §1.2). The call graph is therefore **exactly known** at compile time, and summaries are exact up to the abstractions below.

### 7.1 Summary content

For every user function, method, constructor and operator overload, the compiler computes a **flow-insensitive summary**: a set of effects `(R|W, path, value)` plus flags.

- `path` roots are **formal roots**: `Param(k)` (parameter `k`, or `this` = `Param(0)` for methods/constructors/struct methods), object-family roots `Tree(Param(k))`, the abstract `Graph`, or `Unknown(C)` (object of class `C` reached through memory). Locals, by-value struct/fixed-array parameters (M1 §4.6), and objects allocated inside the callee are **callee-private and excluded** (fixture 011).
- Reads/writes of `Param(k)` of class type, by-reference struct `this` (M2 §3.2), dynamic-array parameters (Gap G-1: treated as by-reference, conservatively) are **kept**.
- `value` is `Const c` or `Unknown` (§7.3).
- Flags: `FILE_IO` (§7.5).
- Effects of callees are included (transitively), instantiated per §7.2.

Computation: least fixed point over the call graph (mutual recursion and self-recursion terminate because the lattice is finite: paths are bounded by declared field paths with `*` collapsing array indices to `Any` beyond depth 4).

### 7.2 Instantiation at a call site

At a call inside a task, each callee effect on `Param(k)` is re-rooted at the corresponding argument's path or origin (§5.3): for class-typed parameters the argument's **origin**; for by-ref struct `this` the receiver's **path** (`a.add(1)` ⇒ `a.total`, fixture 076); for a `Site` origin, that site. Arguments whose origin is `Unknown` produce `Unknown(C)` roots (Possible overlap with any compatible object). The call's site position is the start of the call expression (receiver first token for method calls, §12.2). Argument expressions themselves contribute ordinary reads.

### 7.3 Values in summaries

For each written path in a callee, the summary value is `Const c` iff **every** write to that path anywhere in the callee (transitively) writes the same constant expression `c` that mentions no parameters; otherwise `Unknown`. Arguments are **not** propagated into callees: `set(f, 1)` writes `f.on := v`, which is Unknown (fixture 094), while `setOne(f)` with `f.on = 1` inside is `Const 1` (fixtures 092, 093). Decision (PM directive 5 / RD-M35-04): **a callee's written value is generally not statically known; it is known only when the callee itself writes a literal/constant expression on every write to that path.**

### 7.4 Modules

Summaries are computed over the whole import graph reachable from the main file (all modules are compiled together, M1 §3.1); exported and private functions alike. A conflict located in module `M` is reported with `M`'s path and, if the note is in another module, the note carries its own path (fixture 070; note path = the other module's path as given to farmc). Per-module scoping (M1 §3.1) is unaffected.

### 7.5 File output (`FILE_IO`)

`Renderer.savePNG` and every function whose summary has `FILE_IO` **MUST NOT** be called inside a task (directly or through any call chain) → **E0805** at the call expression inside the task (fixtures 043, 057). `print`/`println` are allowed (buffered, §9). Rationale (OQ-M35-03): file writes are externally visible effects whose relative order between tasks cannot be captured by memory-location analysis (two tasks saving to the same path would be an undetectable race); forbidding them keeps the checker complete. Call `savePNG` after the join.

### 7.6 Checked statically vs. not checked

| Concern | Compile error | Not checked in M3.5 |
|---------|---------------|---------------------|
| Overlapping accesses to memory locations (§5) | E0801/E0802 (+ W0801) | — |
| File output in tasks | E0805 | — |
| Data reached only through external state (files, environment) | — | out of language |
| Deadlock / livelock | impossible (no locks) | — |
| Non-termination in a task | — | the block never joins (same as a sequential infinite loop) |

## 8. Standard-library effects

### 8.1 Built-ins (M1)

`print`/`println`: no location effect (buffered, §9). `str`, `int`, `float`, `len(T[N])`: pure. `len(T[])`: read `a.#len`. `push`: §6.7. Array indexing: §5.2.

### 8.2 `farmos:math` (M2)

- Pure methods (M2 tables, `Mut?` = N): read receiver path and arguments only.
- **Mutating methods** (`Mut?` = Y: `set`, `copy`, `add`, `multiplyScalar`, `normalize`, `invert`, `lerp`, …, including chained receiver-return calls, M2 §3.4): **write the whole receiver path** (`v` for `v.add(w)`, `mesh.position` for `mesh.position.set(…)`) with Unknown value and read the arguments. Stdlib writes are never `Const` (`v.set(0,0,0)` twice is E0801, not W0801).
- `Matrix4.decompose(p, q, s)`: writes its three lvalue arguments.
- Operators and pure struct math: pure.
- Fixtures: 104 (E0801: two mutating methods on `v`), 105 (two different vectors).

### 8.3 `farmos:scene` (M3): classes, sync, and abstract locations

Scene objects are classes (M3 §3.1): object identity via origins (§5.3); overlap is **per field, down to leaf components of inline math structs** (`cube.position.x`, `cube.scale.z`, fixture 078). Beyond ordinary field accesses, the following **normative effect table** applies (paths relative to the object named):

| API | Reads | Writes (value Unknown unless a plain field assignment of a constant) |
|-----|-------|------------------------------------------------------------------------|
| plain field assignment / mutating math method on a field path | per §5.2 / §8.2 | that path |
| **any write to `rotation` (or a sub-path)** | — | additionally **`quaternion`** (whole, Unknown) — M3 §4.2 sync (fixture 077) |
| **any write to `quaternion` (or a sub-path)** | — | additionally **`rotation`** (whole, Unknown) |

| `Scene.setBackground` / `clearBackground` | — | `hasBackground`, `background` |

`Tree(s)` denotes the set of all scene-graph objects reachable from object `s` by `add` (plus the geometry/material objects they reference). Overlap rules for the abstract roots (extending §5.3):

- `Tree(o)` vs `Tree(o')`: Definite if same origin; **Disjoint if they are two different `Site`s that are both *detached*** (fixture 022) — a `Site` is *detached* if every use of every binding with that origin in the enclosing function is a method receiver, a field-path base, or a `scene`/`camera` argument of `Renderer.render`; in particular never an argument of `add`/`addAt` and never passed to another function (otherwise one tree could contain the other); else Possible.
- `Tree(o)` vs an object root `x`: Definite if `x` has origin `o`; **Disjoint if `x` is a *detached* `Site`** (definition above; fixture 022: `cameraA`); otherwise Possible (fixture 073: `mesh` was passed to `scene.add`).
- `Graph` vs `Graph`: Definite. `Graph` is disjoint from every other root.
- Renderer roots are ordinary class roots (`renderer.#frame`): `render` twice on **one renderer** → E0801 (fixture 044); two renderers with distinct `new` sites → independent (fixture 022).

Consequences (normative, tested): **rendering one scene from two tasks is an error even on two renderers** (both write the scene's matrices; fixtures 045, 106); one camera shared by two renders is an error (074); moving an object while a task renders its scene is E0802 (073); two independent renderer/scene/camera triples render concurrently and correctly (022); hierarchy mutations in different tasks always conflict, even on different scenes (098; `Graph` is a global abstraction — false positive accepted, RD-M35-14).

**Non-goal:** M3 scene APIs are not made internally parallel here; a future parallel rasterizer (M4) MUST present the same effect table externally.

## 9. Output ordering (`print` / `println`)

1. Inside a task body (and inside functions called by it, transitively), `print`/`println` write to the **task's private output buffer**, not to stdout.
2. At join, the runtime appends the buffers to the enclosing output stream **in task-index order** (task 1's bytes, then task 2's, …). For a block nested in a task, the enclosing stream is the enclosing task's buffer; for a top-level block it is stdout.
3. Output produced by the parent **before** the block appears before all task output; output after the block appears after (fork/join edges).
4. Within one task, `print` order is program order.
5. Buffers are unbounded (memory-limited). Output from a long task is not visible until the join (documented trade-off; fixture 010).
6. **Sequential equivalence (§4.6) holds for stdout:** the bytes are exactly those of running tasks 1..n one after another.
7. On a **trap** in some task (§10.2): stdout receives the parent output already emitted, then buffers of tasks `1 … t-1` in full, then the trapping task `t`'s bytes up to its trap point; tasks `> t` contribute nothing; then the trap line goes to stderr (fixtures 027, 028, 099).
8. Conflicts are compile-time: there is **no runtime conflict abort**, so no partially-flushed conflicting run exists (RD-M35-01). (Under OQ-M35-02 option C, a trap 109 would discard all task output of the failing block, and output before the block would remain.)
9. stderr is written only by traps and only after the buffers are flushed; tasks have no independent stderr API in M1–M3.

## 10. Control flow and traps

### 10.1 `return` / `break` / `continue`

- `return` inside a task → **E0803** (fixture 040). A task ends by reaching the end of its body. A `return` in a function called by a task is normal (it returns from the callee).
- `break`/`continue` may not cross a task boundary → **E0804** when the nearest enclosing loop-or-task boundary is a task and a loop exists outside (041, 056); loops entirely inside the task are fine (080). With no loop at all, M1's `E0510` is reported.
- A `parallel` statement is not a loop; `break`/`continue` written directly in the parent (outside tasks) refer to the parent's enclosing loop as usual.
- `return` in the parent code after/around the block is unaffected (`return a + b;` after join, fixture 029).

### 10.2 Traps in tasks (deterministic selection)

Runtime traps 101–108 raised inside a task are **task traps**. At the join of a block the runtime resolves them:

1. Wait until every task of the block has finished or trapped (no early exit; a lower-index task that is slow MUST be waited for, fixture 099).
2. Let `t` be the **lowest task index that trapped**. That trap is the block's trap: identical stderr line and exit code as the same trap in sequential code (`runtime error: <message>`, exit 101…108).
3. Output per §9.7; effects of tasks `> t` and of task `t` after its trap are discarded/unobservable because the process exits immediately.
4. A trap raised by a nested block is a trap of the enclosing task (propagates as its trap point) (recursive rule).
5. Whether a higher-index task "would also have trapped" is unobservable. (Fixture 027: task 2 → 101, task 3 → 102; result 101.) Runtimes MAY cancel tasks `> t` early only if no observable difference results.

Consequently the exit code and stderr of a trapping program are the same for every schedule and worker count (AC-M35-09).

### 10.3 Exit code of `main`

Unchanged (M1 §5.6). `main` may contain `parallel` blocks; tasks cannot return values or exit the process.

## 11. Runtime contract

### 11.1 Determinism (normative)

- A program accepted by farmc (no errors) MUST produce **identical stdout, stderr and exit code on every run, for every number of worker threads, and with or without the environment override** (§4.6). Observable behavior MUST NOT depend on worker count, thread scheduling, CPU count, or timing.
- Only performance may vary.

### 11.2 Worker pool

- Default worker count `W = min(max tasks that can run at once, logical CPUs of the host)`, at least 1; a block with `n` tasks uses at most `n` runners.
- **Override:** environment variable `FARMOS_THREADS=<W>` (decimal integer `1 ≤ W ≤ 256`) read by the produced program the first time a parallel block executes. Unset, empty, non-numeric, or out of range ⇒ ignored (default) — never an error. No compiler flag (OQ-M35-06 option A).
- `W = 1` means: no additional threads; the calling thread executes task 1, then task 2, …, in index order (the sequential reference execution).
- Programs that never execute a `parallel` statement MUST NOT read the variable, create threads, or pay any cost.
- Thread creation failure MUST NOT be observable: the calling thread runs the unstarted tasks itself.

### 11.3 Nested blocks, deadlock freedom

A thread that reaches a join (or a nested block) MUST NOT block while any not-yet-started task of that block exists: it **executes those tasks itself** (help-first), then waits only for tasks already running elsewhere. Hence every program terminates (if its sequential execution does) for every `W`, including `W = 1`, including arbitrarily deep recursive blocks (fixture 029, `pfib`).

### 11.4 Task threads

- Tasks run with a stack of at least the main thread's stack size.
- Memory allocation (`new`, `push`, string concat, task output buffers) MUST be thread-safe when a parallel block can run. Program-lifetime arena semantics (M1 §4.7) are unchanged; task-allocated objects live until process exit.
- The main thread's state is visible to tasks at fork, and task writes are visible to the parent after join (§4.5): the runtime MUST include the corresponding memory barriers.

## 12. Diagnostics

### 12.1 Format (amends M1 §8.1)

```
<path>:<line>:<col>: error[E0xxx]: <message>
<path>:<line>:<col>: warning[W0xxx]: <message>
<path>:<line>:<col>: note: <message>
```

- Warning codes use the letter `W` followed by four digits; M3.5 owns **W08xx** (mirroring E08xx). `line`/`col` rules are M1's (1-based, Unicode scalar columns).
- A `note:` line, when present, belongs to the primary diagnostic immediately before it and is printed directly after it. Conflict diagnostics (E0801, E0802, W0801) **always** carry exactly one note that locates the other access. Structural diagnostics (E0803–E0807) have no note.
- Notes use the same path convention as primaries (the path as given to farmc for that file).
- Message templates (text SHOULD match; fixtures assert position and code only):

| Code | Template |
|------|----------|
| E0801 | `conflicting writes to {loc}: task {j} and task {i} write it with different or unknown values` (Possible overlap: `possibly conflicting writes to {loc}: …may write it…`) |
| E0802 | `conflicting read and write of {loc}: task {j} {verb_j} it while task {i} {verb_i} it` (verb ∈ `reads`,`writes`; Possible ⇒ prefix `possibly`) |
| W0801 | `tasks {i} and {j} write the same value to {loc}` (Possible: `may write`) |
| note | `{verb} of {loc} by task {i} is here` (via a call: `… by task {i} through call to `{callee}` is here`) |

### 12.2 Site positions (normative)

The primary/note position of an access site is the **first character of**:

| Site | Position |
|------|----------|
| assignment `lv = e`, `lv ⊕= e` | the first token of `lv` (`a`, `p`, `c`, `this`, `r`) (031, 033, 034) |
| read of a variable/path/element in an expression | the first token of the maximal path expression (`a` in `a + 1`; `xs` in `xs[i]`; `c` in `c.n`) (032, 083) |
| read of an index variable inside `[...]` | that identifier (087) |
| call of a function/method/stdlib | the first token of the call expression: callee name, or the receiver's first token for `recv.m(...)`; for `push(...)`/`len(...)` the name token (038, 039, 054, 081) |
| access of a nested block's task | as above, inside the inner task |
| `new S(...)` struct literal writes (`p = new Pair(1, 2);`) | the first token of `lv` |

Accesses reached through a summary are attributed to the **outermost call inside the task**.

### 12.3 Warnings, exit code, `--werror`

- Warnings are written to **stderr** by `farmc build`/`farmc run` at build time, in the source-ordered stream (§12.4). A build with warnings and no errors **exits 0** and produces the executable; `farmc run` then runs it.
- **`--werror`** (normative, minimal): promotes **all** warnings to errors: each is printed as `error[W0801]` (code unchanged, severity word `error`), its `note:` unchanged, and farmc exits 1 without producing an executable (fixture 100). Without it warnings never affect the exit code.
- Finer control (`-Wno-…`, per-code `--werror=W0801`) is **not** specified (OQ-M35-05).
- farmc exit codes are unchanged (M1 §7.2): 0 success (with or without warnings), 1 any error.

### 12.4 Ordering and stability (normative)

- The full diagnostic set of a compilation is a pure function of the source files (no dependence on threads, hash-map iteration order, or file system order).
- Printed order: sorted by (path as given, line, column, code) of the **primary**, warnings and errors interleaved (fixtures 063, 064, 089, 103). Ties on primary position: `E` before `W`, then code number.
- A cascade limit (M1 §8.2, ≥ 20) applies to errors only; warnings are always all printed.
- farmc MAY analyse in parallel internally but MUST NOT let that affect output (AC-M35-13; `# repeat` on compile fixtures).

### 12.5 Phases and cascades

1. Lex/parse (E0001–E0203, E0806, E0807 in the parser: `parallel`/`task` syntax).
2. M1–M3 semantic checks (types, names, definite assignment, `E0803`/`E0804`, …).
3. Summary computation and **conflict analysis** (E0801, E0802, E0805, W0801). A function is analysed only if it, and every function in its transitive callee closure, passed phase 2 without errors; otherwise its parallel blocks are skipped silently (no cascades; fixture 049 reports only E0504).

## 13. Runtime traps (additions)

**None.** M3.5 adds no new trap: traps 101–108 pass through from tasks (§10.2). Exit code **109 is reserved** for a possible runtime conflict check (OQ-M35-02 option C) and MUST NOT be used for any other purpose. Under the recommended option A it is never emitted.

## 14. CLI and environment summary

- `farmc build|run <file.fm> [-o …] [--emit-c …] [--keep-c] [-v] [--werror]` — `--werror` new (§12.3).
- Produced program: `FARMOS_THREADS=<W>` (§11.2). Nothing else.
- No `-pthread`-style user flag; the driver selects the platform threading primitive internally (Appendix B).

## 15. Size and linking

### 15.1 Unused threading costs nothing (normative)

If no reachable function contains a `parallel` statement:

- the output binary MUST be **size-identical** (SHOULD be byte-identical) to the M3-capable baseline built from the same source by the same toolchain;
- the driver MUST NOT add `-pthread`, thread libraries, thread-local storage, atomics/locks in the allocator, or output-buffering code;
- no thread API import (`CreateThread`, `WaitForMultipleObjects`, `_beginthreadex`, `pthread_*`, `thrd_*`) may appear in the import table.

### 15.2 Budgets

- **Hello world** (`spec/tests/M1/001_hello.fm`) stripped size == M3 baseline (AC-M35-14).
- **2-task demo** (fixture `001_two_tasks_basic.fm`, stripped, Windows x64): **≤ hello + 12 KiB** (OQ-M35-04 option A, recommended); option B: ≤ hello + 24 KiB.

### 20.1 Contradictions / tensions with PLAN.md and earlier specs

1. **PLAN.md M3.5** says a conflicting write "must be reported" and lists detection point as open: resolved as compile-time (PM decision). PLAN's phrase "at the same time" suggests a runtime notion; the spec's static model reports conflicts that may never coincide in time (§6.8), by design.
2. **PLAN.md** AC draft says "conflicting a=1 / a=2 raises the defined error deterministically": satisfied by compile error E0801 (exit 1), not a runtime exit code. AC-M35-03 is a compile-error AC; no runtime trap number is consumed (109 reserved).
3. **M1 §1.2** listed "Async, threads, atomics" as post-M1: superseded for threads (amendment 2).
4. **M1 §2.5** future-reserves `async`/`await`: unchanged and irrelevant to the structured block (OQ-M35-01 B would need to un-reserve `await`).
5. **M1 §8.1/M1 fixture format** only checks `# error:` lines and knows no warnings/notes; extended in tests/M3.5/README.md only.
6. **M3 §4.5** `renderer.render` calls `scene.updateMatrixWorld(true)`, i.e. `render` *mutates* the scene: this is why rendering one scene from two tasks is a conflict even with two renderers (§8.3). This is a consequence of M3, not a change to it.
7. **M2 §3.2** by-reference struct `this` (mutating methods) makes `v.add(w)` a write of `v`: two tasks each calling a mutating method on the same vector is E0801 (fixture 104).

## 21. Known gaps and notes

- **G-1 (M1 gap):** M1 does not state whether assigning/passing a dynamic array `T[]` copies the buffer or aliases it (§4.5 says "arena-backed growable storage for the owning binding's data buffer"). The M3.5 checker is sound under both readings (§4.4). PM decision 2026-09-29: tracked as an M6 cleanup item, not changed in M1 now; not required for M3.5.
- **G-2:** M3 §5 says `Scene` "is-a" `Object3D` for stdlib purposes; §5.3 uses the family relation for "compatible classes" (any two Object3D-family classes may alias).
- **G-3:** The analysis is intraprocedural on origins (§5.3): a class object passed through several helper functions is tracked by parameter identity (`Param(k)`); at a call site the actual origin is substituted (§7.2). Objects stored in and loaded from arrays/fields are `Unknown` origin (Possible overlap with everything compatible).
- **G-4:** A conflict-free program whose two tasks write different fixed-array elements still has **false sharing** at the cache level; performance only.

## Appendix A — Usage and porting notes (non-normative)

### A.1 Idioms

**Fan-out/fan-in (results in distinct slots):**

```
let r: int[4] = [0, 0, 0, 0];
parallel {
  task { r[0] = work(0); }
  task { r[1] = work(1); }
  task { r[2] = work(2); }
  task { r[3] = work(3); }
}
```

**Range split (proved disjoint by counted-loop intervals, fixture 007):** `for (let i = 0; i < 4; i += 1) { a[i] = …; }` in task 1 and `for (let i = 4; i < 8; i += 1) { a[i] = …; }` in task 2.

**Parallel scene preparation:** two independent `Renderer`/`Scene`/`PerspectiveCamera` triples (distinct `new` sites) render concurrently (fixture 022); `savePNG` after the block.

**Divide and conquer (fixture 029):** recursive `parallel` with a sequential cutoff.

### A.2 Fixing a reported conflict

| Diagnostic | Typical fix |
|------------|-------------|
| E0801 on `a = 1` / `a = 2` | Give each task its own variable/slot, combine after the join. |
| E0801 on `a += 1` in two tasks | Accumulate in task-private locals; add them after the join (`x = a1 + a2;`). |
| E0801/E0802 on `a[i]`/`a[j]` (Possible) | Use counted-loop ranges, constant indices, or `a[i]` / `a[i + c]` with an invariant `i`; or split into separate arrays. |
| E0801 on `push` | One array per task, concatenate after join. |
| E0802 read vs write | Read first, then start the block (copy to a `const`), or write to a different location. |
| E0801 on `render`/`add` | Only one task touches a scene/renderer/camera; use separate triples, or run sequentially. |
| W0801 | Remove the redundant second write. |

### A.3 Three.js note

Three.js/JS has no shared-memory threads (Web Workers copy). Farmos tasks are closer to Go's `errgroup`, Rust's `std::thread::scope`, or C#'s `Parallel.Invoke`. Because tasks share memory but conflicts are rejected statically, ports can keep mutation-heavy Three.js style (`mesh.position.x = …`) as long as each task owns distinct objects/fields.

## Appendix B — Implementation notes (non-normative)

- **Windows x64:** either Win32 (`CreateThread` / `WaitForMultipleObjects` / `SetEvent`) or C11 `<threads.h>` when the clang/gcc toolchain provides it (MinGW-w64's `<threads.h>` support is uneven; prefer Win32). The language rules are backend-neutral.
- **Emission:** each `task` body becomes a static C function taking a pointer to a compiler-generated struct of pointers to the captured locations ("environment by reference"); the struct lives on the parent's stack (safe: join before return). Task bodies are not closures in the language sense.
- **Pool:** lazily created on the first executed `parallel`; help-first join (§11.3); a block with one runner (`W = 1`) reduces to plain calls in task order.
- **Output buffers:** created per task lazily on first `print`; append to parent stream at join. Programs whose tasks never print need no buffer code (DCE).
- **W0801 stores:** emit plain stores (equal values) or, if the backend wants zero UB, relaxed atomic stores; either is conforming.
- **Size:** the threading runtime is a separate object/section set referenced only by emitted `parallel` code; `--gc-sections` + no `-pthread` keeps hello unchanged. Avoid pulling the whole CRT thread layer (`_beginthreadex` vs `CreateThread`) if size matters.
- **Analysis:** summaries via bottom-up SCC order over the call graph; locations as (root, step*) tuples interned per compilation unit; O(sites²) per block is fine (≤ 256 tasks).
